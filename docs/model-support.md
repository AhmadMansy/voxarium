# Model support in Voxarium

This note describes what the multi-model studio ships today, which gates are
enforced, and how to extend the registry. Planned work is described in the milestone
plans in this folder.

## Design rules

- **One registry, one source of truth.** `electron/models/manifests.json` is
  generated by `scripts/build-manifests.mjs` and imported by both Electron and the
  renderer. The renderer never hard-codes model or voice URLs; it asks the manifest
  for file names and builds `/model/<id>/<file>` requests.
- **Visible does not mean runnable.** Every selected model appears in the Models
  page with its fit, license, capabilities, score and evidence. A model whose runtime
  pack is absent stays visible and explains exactly why it cannot be activated.
- **No silent activation.** Restricted licenses need a per-model acknowledgment
  pinned to the current license ID. Failed loads and denied switches leave the
  previous model active.
- **Honest runtime reporting.** Runtime readiness is computed from what is actually
  installed on the machine, not from a static manifest flag. A model only activates
  once its runtime is installed and its files are verified.
- **Small installer, separate downloads.** The app installer contains no Python
  interpreter and no multi-gigabyte model weights. Runtimes are downloaded or built on
  demand from pinned recipes, weights are verified against pinned hashes, and both are
  installed atomically under the user's data folder.

## First-run setup

The first-run assistant (`src/components/SetupWizard.tsx`) is a two-step model chooser:

1. **Choose a model.** All 17 registry entries are listed with their score, hardware
   fit, license badge and truthful runtime status. Search matches names, families,
   languages and tags. Installed and active models stay visible, and selecting a
   gated model is allowed so its status can be reviewed.
2. **Configure the selection.** The panel shows the model description, fit reasons,
   language count, license summary and runtime gate. Phonon 31M exposes Q8/F32 quality
   options; restricted licenses require an explicit acknowledgment before the main
   process will download or import. Gated models can only be inspected or opened in
   the Models page — the download button stays disabled.

A successful download/import marks setup complete and activates the selected model
when it is not already active. Setup never hides a missing runtime, never downloads
unpinned files, and never marks a model ready before the engine reports `ready`.
Closing with “Set up later” records `onboardingDismissed` so the same dialog does not
reappear on every launch; the Models page and sidebar setup button remain available.

### Windows-specific workarounds

- **Visual C++ runtime.** ONNX Runtime and PyTorch need `msvcp140.dll` /
  `vcruntime140_1.dll`, which many machines lack. Every environment installs the
  `msvc-runtime` wheel and `start.py` registers it with `os.add_dll_directory`, so
  no admin installer is required.
- **SILMA / `pynini`.** `nemo_text_processing` depends on `pynini`, which has no
  Windows build. The recipe drops it with a uv override and ships a pass-through
  `nemo_text_processing` shim (`electron/sidecars/shims`); number normalization is
  disabled and SILMA's own `cached_path` is redirected to the verified local files.
- **Japanese G2P.** misaki's default backend needs a UniDic dictionary that only
  builds from source; the Kokoro adapter uses misaki's `pyopenjtalk` backend with
  the `pyopenjtalk-plus` wheel instead.
- **Python 3.11.** IndexTTS2 declares `<3.12`; uv provisions a managed 3.11.
- **Long paths.** setuptools fails past 260 characters. When the default uv cache
  path is long, the builder uses `<drive>\VoxariumCache\uv` instead.
- **Process lifetime.** Servers watch `VOXARIUM_PARENT_PID` and exit with the app.
  (A blocking read on a stdin pipe deadlocks DLL loading on Windows.)

## The install contract

Every model, whatever its runtime or the operating system, follows the same seven stages
(`src/models/pipeline.ts`). Stages that do not apply are skipped, never reordered, and the
Models page shows them under **Details → Install steps**.

| # | Stage | What happens | Phonon (in-app) |
| --- | --- | --- | --- |
| 1 | Check this computer | Disk space, memory, GPU fit, platform support tier, Hugging Face access | yes |
| 2 | License | Review and accept restricted licenses | when restricted |
| 3 | Toolchain | Pinned uv and Python | skipped |
| 4 | Environment | The model's isolated venv from a pinned recipe | skipped |
| 5 | Model files | Pinned weights, size + SHA-256 verified | yes |
| 6 | First start | Load once; helper files may be fetched | skipped |
| 7 | Test synthesis | Speak a fixed sentence and check the audio | engine check |

`planInstall` turns what the app already knows into the stage list, a list of **blockers**
(unsupported platform, not enough disk, model too heavy, missing Hugging Face token) and
**warnings** (experimental tier, CPU fallback, watermark, first start downloads).

The test synthesis (`electron/models/verify.cjs`) starts the sidecar, asks it to say
"Voxarium is ready to speak." and checks the audio for plausible duration, level, clipping
and invalid samples. The result is stored with the install record and shown on the model
card as *Test passed* or *Test failed*. It is a smoke test, not a quality judgement, and it
does not block activation yet.

`node scripts/smoke-sidecar.mjs <modelId>` runs stages 3 to 7 headlessly through the same
managers the app uses. The **Sidecar smoke test** workflow runs it weekly for Supertonic 3
and Kokoro on Windows, Linux and macOS; a green run is the evidence for that model's
support tier on that system.

## Download and install lifecycle

`electron/models/downloads.cjs` owns a per-model state machine:

```
not-installed -> downloading -> verifying -> installed
                       |            |
                       +--> error <-+
installed -> update (when a pinned file changes)
```

- Downloads stream to `models/.staging/<id>/<file>.part`, resume from the existing
  byte count, and are cancelled through `AbortController`.
- Every completed file is checked against its manifest byte size and SHA-256 before
  it is moved into `userData/models/<id>/`. A hash or size failure deletes the part
  file and leaves the previous install untouched.
- Installs are atomic per file (`rename`, with copy+remove fallback across volumes).
- `verify` re-hashes installed files. `import` copies a user-supplied folder through
  the same checks. `uninstall` removes only that model's directory.
- The Models page shows per-file progress, quality, lifecycle, and a real download
  byte count. The model card score is the product rating (1–10) with the rubric and
  evidence link; hardware fit is shown separately.

## Runtime packs

Model weights and runtimes are separate. `electron/models/runtimes.json` declares
the packs and `electron/models/runtimes.cjs` installs them under
`userData/runtimes/<id>/`.

| Kind | Purpose | Install |
| --- | --- | --- |
| `tool` | uv 0.13.6, which builds every model environment | Pinned zip (size + SHA-256) |
| `python` | CPython 3.12.16 from python-build-standalone | Pinned tar.gz (size + SHA-256) |
| `sidecar` | One isolated venv per model + the Voxarium adapter | Built from a pinned recipe |

Installing a sidecar model installs whatever is missing in order: uv → Python →
the model's environment → the model's weights. The Models page shows each step.

### Building a sidecar pack

1. `uv venv --relocatable` with the managed interpreter (or a uv-managed Python
   for recipes that need another version).
2. `uv pip install` of the recipe's requirements, plus `torch==X+<variant>` from
   the matching PyTorch index and `msvc-runtime`. The uv cache is shared and hard
   linked, so PyTorch is stored once even when several models use it.
3. Pinned source archives (`sources`) are downloaded, checked against their
   SHA-256 and extracted to `src/<name>` (put on `sys.path` by `start.py`).
4. `electron/sidecars/voxarium_sidecar.py`, the model's adapter, assets and any
   shims are copied to `app/`, and `start.py` is generated.
5. `start.py --check` imports the adapter's dependencies. Only then is the tree
   given its marker and swapped into place atomically.

Uninstalling uv or Python is refused while a model environment still uses it.

### Sidecar protocol

The supervisor (`electron/models/sidecar.cjs`) starts
`venv/Scripts/python.exe start.py --host 127.0.0.1 --port 0 --model-dir <dir>` (`venv/bin/python` on Linux and macOS)
with a random 32-byte token. The server prints `VOXARIUM_READY {"port": N}` as
soon as it listens, then loads the model in the background. `GET /health` reports
`{ready, stage, error, device}`; `GET /voices` lists the model's voices plus the
user's reference clips; `POST /synthesize` returns base64 float32 PCM resampled
to 24 kHz. Every request needs the bearer token.

The first start of a model runs with `--prepare`: auxiliary assets (vocoders,
codecs, G2P dictionaries) may be fetched, a test sentence is generated, and a
`.voxarium-prepared` marker is written. Every later start sets `HF_HUB_OFFLINE`,
`TRANSFORMERS_OFFLINE` and `HF_DATASETS_OFFLINE`. All caches (`HF_HOME`,
`TORCH_HOME`, `MODELSCOPE_CACHE`, …) live inside the model folder, so removing a
model removes them too.

### Voices and reference clips

Sidecar models report their own voices (built-in speakers, voice-design presets,
or a synthetic reference for clone-only models). They are registered in the
catalog as `<modelId>:<voice>` and are only compatible with that model.
Clone-only models default to `electron/sidecars/assets/reference-en.wav`,
Kokoro's Apache-2.0 synthetic `af_heart_0.wav` sample (verified against its git
blob hash). Users can add their own clips to `userData/voices/references`
(audio plus an optional `.txt` transcript); they appear after the model reloads.

## Hardware fit

`src/models/fit.ts` scores the live hardware profile into four levels:

| Level | Meaning |
| --- | --- |
| `great` | Meets the recommended RAM/VRAM and disk targets |
| `runs` | Meets the minimum, below the recommendation |
| `cpu` | Sidecar model without the preferred GPU; expect slow CPU inference |
| `too-heavy` | Below minimum RAM or insufficient free disk |

Every level includes human-readable reasons (“Needs about 16 GB of RAM; this
machine reports 8 GB”). Sidecar models also show VRAM requirements, and the download
button is disabled when the disk check fails. Hardware is sampled in Electron
(`electron/models/hardware.cjs`), including GPU preference and a WebGPU likelihood
signal.

## License gates

- `requiresLicenseAck` is true for restricted, review-required, or explicitly
  non-commercial licenses.
- `licenseAcknowledged` requires an acknowledgment for the **same license ID**;
  changing a model's license invalidates old acknowledgments.
- Restricted models carry a visible badge and an acknowledgment gate in the Models
  page and setup flow. Activation and import re-check the gate in the main process,
  so renderer bypasses cannot silently enable a restricted model.
- `models:activate` and `models:import` also enforce runtime readiness (via the
  installed runtime packs) and pinned files. The legacy setup path keeps working
  against the active model.

## Capability gating

Capabilities come from the manifest and drive the UI:

- **Languages:** only manifest languages appear. Unsupported saved languages are
  normalized to the model default.
- **Arabic:** the Arabic chip appears only when a model declares Arabic in its
  language list. Modern Standard Arabic is the default variety. The variety
  sub-selector is shown only where the model supports more than one variety; in the
  shipped set that is OmniVoice. `capabilities.arabic` is intentionally not used as
  the inference source, so Supertonic's `ar-sa` declaration is preserved even though
  its flag is false.
- **Voices:** `VoicePicker` and `VoicesPage` group by model compatibility. Phonon
  voices require a Phonon-format model and a matching locale; incompatible rows stay
  visible but disabled with a reason. Imported custom embeddings are validated
  against the selected model's format.
- **Add a voice:** the dialog depends on the active model. Models with a voice-file format import a
  `.safetensors` file; models that clone from a recording (`cloneKind: 'local'`) read a clip placed in the
  references folder; other models say they use a fixed set of voices. Everything happens on the
  computer: Voxarium has no cloud cloning and uploads nothing.
- **Dialogue/emotion/streaming/normalization/speed:** each control is hidden or
  disabled with a reason when the active model does not support it.
- **Batch:** validates every line's voice and language against the active model,
  blocks generation for incompatible rows, and offers “Switch all” to the model's
  default voice.
- **History:** each take stores `modelId`, `modelName`, `runtime`, `license` and
  capability data. “Reuse settings” restores model, voice and language.

## Per-model settings

Top-level generation settings mirror the active model. Each model's preferences are
archived in `settings.modelSettings[id]`:

- `switchModelSettings` archives the outgoing model and restores the incoming
  model's setup in one patch, including language, quality, device, temperature,
  seed, voice, streaming and Arabic variety.
- `rememberPreferences` keeps the active model's archive in sync when a setting is
  edited, without rewriting unrelated app settings.
- Switching is rolled back if loading or activation fails; the previous model stays
  selected and its settings remain intact.

## Testing

```powershell
npm.cmd run typecheck   # TypeScript strict
npm.cmd test            # 22 model-layer unit tests
npm.cmd run build       # typecheck + production bundle
npm.cmd run test:e2e    # Electron lifecycle smoke test
```

`scripts/test-models.mjs` loads the TypeScript modules through Vite's SSR loader
(no second test runtime). It covers:

- Registry integrity, unique IDs, default fallback, and pinned revisions; every file
  pinned by SHA-256, git blob SHA-1 or LFS-pointer id.
- Every model installable: Phonon in-app, the rest through a buildable sidecar pack;
  gated repos flagged for a token.
- Quality discovery from manifest files.
- Fit levels and reasons for RAM, disk and sidecar VRAM.
- License acknowledgment freshness, badges, and install gates.
- **OmniVoice** weights marked CC-BY-NC with acknowledgment required.
- **Runtime catalog**: pinned uv and Python 3.12.16 archives, 13 sidecar recipes with
  pinned requirements, PyTorch versions and source archives, and an adapter (plus any
  shims) that ships with the app for every sidecar model.
- **Dynamic runtime readiness** derived from installed packs; license gate accepts
  readiness; archive path traversal rejected; safe `.tar.gz` extraction.
- Arabic inference from declared languages, MSA defaults, and varieties.
- Voice compatibility for built-in and custom Phonon voices.
- Preference normalization, archive/restore on switch, and archive mirroring.

`scripts/test-electron.mjs` launches the built app with `VOXARIUM_USER_DATA` pointing
at a temporary profile. It hard-links complete Phonon files into the staging folder,
so the real downloader exercises SHA-256 verification and atomic install without
network access. The flow is:

```
first-run chooser -> inspect gated model -> setup install -> verify -> activate -> synthesize -> visit every page -> switch refusal -> uninstall
```

It also asserts that the chooser lists all 17 models, that a gated model exposes its
license and the Hugging Face gate, that the **Runtime packs** panel lists all 17 packs
(uv, Python and 13 buildable sidecars), that a fresh profile can install and activate Phonon 31M
from setup, that a refused switch leaves the previous model active, that Settings
reports the active model and runtime, and that the renderer reports no console or
page errors while visiting the studio, models, voices, history, batch and settings
pages. The fixture source defaults to `%APPDATA%\Voxarium\models`;
override it with `VOXARIUM_E2E_MODEL_DIR`.

Sidecar builds were proven on Windows by building packs with the real runtime manager,
downloading weights with the real model manager, and starting them through the real
supervisor: first-run prepare, a `401` without the token, voice listing, synthesis,
and an offline restart.

## Extending a model

1. Add or update its entry in `scripts/build-manifests.mjs` and regenerate
   `electron/models/manifests.json`.
2. Add a `pins` entry (revision + file selection). The builder pins every file's size
   and hash from the Hugging Face tree. Never ship `files: []` as if it were installable.
3. For a sidecar model, add a recipe to `runtimes.json` and an adapter in
   `electron/sidecars/adapters` exposing `load(ctx)`, `voices()` and `synthesize()`.
   Check the recipe resolves for Windows with `uv pip compile --python-platform
   x86_64-pc-windows-msvc`.
4. Keep restricted licenses flagged so the acknowledgment gate and badge remain.
5. Build the pack, install the model and synthesize through the supervisor before
   shipping it.
6. Add unit coverage for any new language, voice format, capability or fit rule.
7. Run all four test commands above before shipping.

## Current limitations

- **Gated models need a token.** Phonon 40M and OpenAudio S1-mini are gated on
  Hugging Face. Accept the terms on the model page and add a read token in
  Settings › Model downloads. Their files are pinned by the git id of each LFS
  pointer (Hugging Face hides the SHA-256 from anonymous callers); the pointer
  binds the content SHA-256 and size, so the check is just as strict.
- **First start needs the network.** Some libraries fetch auxiliary assets the
  first time they load (SILMA's Vocos vocoder and tashkeel model, IndexTTS2's
  w2v-BERT/MaskGCT/CAMPPlus/BigVGAN, MOSS's audio tokenizer). After the first
  successful start every model runs offline.
- **Heavy models on small GPUs.** Each adapter declares the VRAM it needs and
  falls back to the CPU when the GPU is smaller. That works, but MOSS-TTS (8.5B),
  Breeze TTS 2 and VoxCPM2 are slow on CPU, and MOSS needs about 20 GB of free RAM.
- **Disk.** A CUDA environment is 4–6 GB before weights. uv hard-links PyTorch
  from its cache, so additional models that share a PyTorch version cost much less.
- **Linux/macOS.** `uv` and CPython are pinned per platform (`win32-x64`, `linux-x64`,
  `darwin-arm64`, `darwin-x64`) and every sidecar declares a support tier per platform in
  `runtimes.json` (`A` verified, `B` builds, `C` experimental; missing means unsupported).
  Only Kokoro, Supertonic and Piper are `B` on Windows; everything on Linux and macOS is `C` until a
  smoke test runs there. macOS runs sidecars on the CPU (no MPS yet), and Intel Macs get only
  recipes without PyTorch because PyTorch publishes no recent macOS Intel wheels.
- **Verification depth.** Every recipe is checked to resolve on Windows x64 with
  binary wheels (or pure-Python sources). Supertonic and Kokoro were built,
  downloaded and synthesized end to end on Windows; the larger models share the
  same build and server path but were not each run end to end during this change.
